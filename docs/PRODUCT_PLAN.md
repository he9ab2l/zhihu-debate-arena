# 知乎思辩台 · 产品说明计划书

## 一、产品概述

知乎思辩台是一款面向学习、职业与生活选择的证据驱动决策工具。它把知乎社区中分散、异质、带有个人经验色彩的讨论，转换成一个更适合决策前阅读的工作台：先呈现支持与质疑两种阅读视角，再通过三回合交锋暴露隐含前提，最后生成不替用户做决定的行动检查清单。

产品的核心判断是：复杂问题通常不缺观点，缺的是观点之间的结构，以及把观点放回个人约束条件中的过程。因此，产品不输出“正确答案”，而是帮助用户回答“在什么条件下，这个选项值得我选择”。

## 二、用户痛点

用户在知乎上搜索职业、学习或人生选择时，常见问题包括：结果数量太多，难以形成结构化比较；高赞内容不一定适合自己的资源与阶段；赞成和反对观点分散在不同问题、不同回答中；搜索摘要容易被误读成完整立场；看完大量内容后，仍然不知道下一步该验证什么。

知乎思辩台将这些问题拆成三层：**证据层**保留来源与上下文入口，**交锋层**把冲突条件显式化，**行动层**将结论转译成低成本试验、止损线与复盘点。

## 三、目标用户

首批用户是处于选择节点的学生、初入职场者、转行者与独立创作者。他们通常愿意阅读长内容，但缺少时间把多种经验整理成可比较的判断框架。第二阶段可扩展到团队讨论、课程研讨与内容创作者的选题研究。

## 四、核心用户流程

1. 用户输入一个具有冲突条件的议题，例如“第一份工作优先成长速度还是生活确定性”。
2. 服务端优先调用知乎开放平台站内搜索，并对结果进行字段归一化。
3. 系统将检索结果保留为证据卡，展示标题、摘要、作者、内容类型、原文 URL 与可用的互动指标。
4. 系统把结果组织成支持视角和质疑视角，但明确说明这两个标签是产品阅读视角，不是作者自称立场。
5. 用户阅读“立论—攻防—终局”三回合，逐层检查双方的隐含前提。
6. 用户使用行动前检查清单，结合自己的现金流、时间、安全垫与退出成本做决定。

## 五、产品原则

**来源优先。** 只要展示真实知乎论据，就必须保留原文链接；搜索摘要不等于全文，界面持续提醒用户核验上下文。

**不伪造。** Access Secret 缺失、接口失败、额度耗尽时，产品宁可减少信息，也不补写虚构作者、赞同数、回答或额度。

**不替用户投票。** 双方视角的目的，是帮助用户看见分歧结构，而不是建立一个假装客观的胜负分数。

**可逆试验。** 最终建议优先落到小规模验证、时间盒、止损线与复盘点，而不是抽象的鸡汤式结论。

## 六、技术与安全方案

前端采用 React 19、Vite、Tailwind 4 与 tRPC 11；服务端采用 Express 4、Node.js 与 Drizzle；数据存储使用托管 MySQL/TiDB。知乎开放平台调用全部发生在服务端，采用 Access Secret Bearer 鉴权与 `X-Request-Timestamp`。Secret 由托管平台密钥管理，前端只获得脱敏的连接状态。

数据库保存辩题元信息与结构化 JSON，不复制知乎全文。接口返回的摘要按“检索摘要”处理，页面提供知乎原文链接。创建接口按来源地址做轻量限流，并将搜索失败、鉴权失败、频率限制和网络超时转化为用户可理解的降级状态。

## 七、版本计划

| 阶段 | 目标 | 交付 |
| --- | --- | --- |
| V1 当前版本 | 真实检索闭环与可用 Demo | 站内搜索、热榜、额度、证据库、三回合交锋、响应式 UI、服务端 Secret、持久化辩题 |
| V1.1 | 增强可核验性 | 证据按时间/互动指标筛选、原文跳转回溯、搜索请求与结果摘要的审计记录 |
| V1.2 | 增强个性化 | 登录后的历史辩题、收藏、用户自定义判断维度、同一议题多次检索对比 |
| V2 | 团队讨论 | 可分享只读辩题、多人标注证据、异步评论、团队复盘报告 |
| V2.1 | 辅助生成 | 在用户明确开启后调用知乎直答模型生成“中立摘要草稿”，所有模型输出继续与原始证据分离并标注为生成内容 |

## 八、成功指标

短期关注首次生成成功率、证据卡打开率、三回合完成率和检查清单被复制/分享的比例；中期关注同一用户二次生成率、用户主动打开原文的比例以及演示模式到真实凭证模式的切换率。质量评估以来源完整性、摘要与原文一致性、降级诚实度和用户对“是否更清楚自己该验证什么”的主观评分为主。

## 九、风险与对策

知乎内容具有时间性和个体经验偏差，产品不把高赞视为真理，并在 UI 中保留时间与原文入口。开放平台存在额度与频率限制，产品使用缓存、按需请求和明确的额度面板。用户可能误把产品阅读视角当作作者立场，因此所有证据卡和三回合卡片均使用“支持视角/质疑视角”而不是“正方回答/反方回答”。
